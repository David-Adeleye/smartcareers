## 1. Purpose

This document defines the data model for the SmartCareers MVP (Job Seeker Intelligence Platform).

The data model is designed to:

- support explainable, auditable AI decisions  
- persist all user interactions and AI outputs  
- enable history, debugging, and trust  
- support performance and quality metrics  
- scale incrementally without disruptive schema changes  

The database technology is PostgreSQL.

---

## 2. Design Principles

- PostgreSQL is the single source of truth  
- No ephemeral or in-memory-only state  
- AI inputs and outputs are always persisted  
- Explainability artifacts are first-class data  
- JSONB is used for flexible AI outputs  
- All data is strictly scoped by user_id  
- Latency and lifecycle metrics are measurable  

---

## 3. Entity Overview

The MVP data model consists of four core entities:

- users  
- cv_documents  
- analysis_tasks  
- analysis_results  

Each entity has a single, well-defined responsibility.

---

## 4. users

Stores authenticated users.

### Fields

- id (UUID, PK)  
- email (string, unique, indexed)  
- password_hash (string)  
- created_at (timestamp)  
- updated_at (timestamp)  

### Notes

- Contains authentication-only data  
- User profile enrichment is out of scope for MVP  
- OAuth fields may be added in later phases  

---

## 5. cv_documents

Stores uploaded CV files and extracted content.

### Fields

- id (UUID, PK)  
- user_id (UUID, FK → users.id)  
- file_name (string)  
- file_type (enum: pdf, docx)  
- file_url (string)  
- raw_text (text)  
- structured_data (JSONB)  
- created_at (timestamp)  

### structured_data (JSONB)

Contains extracted, verified CV facts used for grounding:

- roles  
- companies  
- employment dates  
- skills  
- achievements  

This data is immutable per document and is the foundation of explainability.

---

## 6. analysis_tasks

Represents a single asynchronous analysis request.

### Fields

- id (UUID, PK)  
- user_id (UUID, FK → users.id)  
- cv_document_id (UUID, FK → cv_documents.id)  
- job_title (string)  
- company (string, nullable)  
- job_url (string, nullable)  
- job_description (text)  
- status (enum: pending, running, completed, failed)  
- retry_count (integer, default = 0)  
- error_code (string, nullable)  
- error_message (text, nullable)  
- started_at (timestamp, nullable)  
- completed_at (timestamp, nullable)  
- created_at (timestamp)  
- updated_at (timestamp)  

### Notes

- One task represents one CV × one job description  
- retry_count tracks transient failures and controlled retries  
- started_at and completed_at enable precise latency metrics  
- status drives frontend polling and lifecycle visibility  
- Failures are explicit and persisted for auditability  

---

## 7. analysis_results

Stores the explainable match output for a completed task.

### Fields

- id (UUID, PK)  
- task_id (UUID, FK → analysis_tasks.id, unique)  
- user_id (UUID, FK → users.id)  
- overall_score (integer, 0–100)  
- breakdown (JSONB)  
- requirements_analysis (JSONB)  
- strengths (JSONB)  
- gaps (JSONB)  
- recommendations (JSONB)  
- prompt_version (string)  
- created_at (timestamp)  

### Notes

- One-to-one relationship with analysis_tasks  
- Schema mirrors the ExplainableMatchScore contract  
- Results are stored exactly as generated by the AI pipeline  
- prompt_version enables quality audits and rollback  

---

## 8. JSON Field Responsibilities

### breakdown (JSONB)

Stores per-category scores:

- skills_match_score  
- experience_match_score  
- seniority_match_score  
- keyword_alignment_score  

### requirements_analysis (JSONB)

Stores per-requirement evidence mapping:

- requirement text  
- status (matched / partial / missing)  
- CV quote (or null)  
- explanation  

This is the core explainability artifact.

---

## 9. Relationships

- users → cv_documents (one-to-many)  
- users → analysis_tasks (one-to-many)  
- cv_documents → analysis_tasks (one-to-many)  
- analysis_tasks → analysis_results (one-to-one)  

All relationships are strictly user-scoped.

---

## 10. Indexing Strategy (MVP)

Recommended indexes:

- users.email (unique)  
- cv_documents.user_id  
- analysis_tasks.user_id  
- analysis_tasks.status  
- analysis_tasks.created_at  
- analysis_results.user_id  
- analysis_results.created_at  

These indexes support:

- dashboards  
- history views  
- latency analysis  
- progress reporting  
- visa and funding audit narratives  

---

## 11. Data Retention and Auditability

- All analysis inputs and outputs are persisted  
- No AI decision is transient  

Enables:

- debugging and root-cause analysis  
- user trust and transparency  
- future compliance requirements  
- longitudinal career improvement reports  

Deletion and anonymisation policies may be added later.

---

## 12. Out of Scope (MVP)

The following are explicitly excluded from the MVP data model:

- recruiter accounts  
- job postings  
- user feedback tables  
- billing and subscriptions  
- analytics event streams  

These belong to Phase 2 and beyond.

---

## 13. Definition of Done

The data model is complete when:

- all MVP features map cleanly to entities  
- explainability data is fully persistable  
- latency and lifecycle metrics are measurable  
- schema aligns with PRD, architecture, and API contract  
- no future feature requires destructive schema changes
